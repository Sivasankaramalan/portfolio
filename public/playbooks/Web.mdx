## 1. Environment Setup

### Prerequisites
- Node.js: v18+ LTS (required for Playwright 1.61.x and modern tooling)
- Java: JDK 17+ (required baseline for Selenium 4.4x bindings)
- Browsers: Chrome, Firefox, WebKit/Safari (Playwright ships its own patched builds; Selenium drives system-installed browsers)
- Git & a package manager: npm/pnpm for JS stacks, Maven/Gradle for Java stacks

### System Requirements
```bash
# macOS
brew install node
brew install openjdk@17
brew install --cask google-chrome firefox

# Windows
choco install nodejs-lts
choco install temurin17
choco install googlechrome firefox

# Linux (Debian/Ubuntu)
sudo apt update && sudo apt install -y nodejs npm openjdk-17-jdk
sudo apt install -y chromium-browser firefox
```

### Choosing a Stack
- Playwright: single API across Chromium, Firefox and WebKit, auto-waiting, network interception and tracing built in — the default choice for new suites in 2026
- Selenium 4.x: broadest real-browser and Grid ecosystem, W3C WebDriver standard, best when you need vendor-neutral driving of real installed browsers or legacy browser support
- Many enterprise suites run both: Playwright for fast local/CI feedback, Selenium Grid for cross-browser device-lab coverage

## 2. Architecture & Core Concepts

### Selenium WebDriver Architecture
```text
┌─────────────┐   W3C WebDriver   ┌───────────────┐   Native/CDP    ┌────────────────┐
│ Test Client │ ─────HTTP/JSON──→ │ Browser Driver│ ───Automation──→ │ Browser Process│
│ (Java/JS/   │                   │ (chromedriver,│    Protocol      │ (Chrome/FF/    │
│  Python/C#) │ ←────Response──── │  geckodriver) │ ←──────────────  │  Edge/Safari)  │
└─────────────┘                   └───────────────┘                  └────────────────┘
```
- WebDriver protocol is the W3C standard (JSON Wire Protocol is legacy/deprecated)
- Each browser vendor ships/maintains its own driver binary (chromedriver, geckodriver, msedgedriver, safaridriver)
- Selenium Manager (bundled since 4.6, GA in 4.11+) auto-discovers, downloads and caches the correct driver/browser pairing — no more manual `PATH` wrangling

### Playwright Architecture
```text
┌─────────────┐   WebSocket/Pipe   ┌────────────────┐   CDP/BiDi/    ┌────────────────┐
│ Test Runner │ ──────────────────→ │ Playwright     │ ─Custom Proto─→ │ Browser Engine │
│ (@playwright│                     │ Driver process │                 │ (Chromium/     │
│  /test)     │ ←──────────────────  │ (Node binary)  │ ←──────────────  │  Firefox/WebKit)│
└─────────────┘                     └────────────────┘                  └────────────────┘
```
- Playwright talks to each engine over its own low-level protocol (CDP for Chromium, custom patched protocols for Firefox/WebKit) instead of the WebDriver wire protocol
- Every test gets an isolated `BrowserContext` (equivalent to an incognito profile) — near-zero overhead for full isolation
- Ships browser binaries itself, so version drift between "the browser on my machine" and "the browser in CI" disappears

### WebDriver BiDi (the convergence point)
- The [WebDriver BiDi](https://w3c.github.io/webdriver-bidi/) spec adds a bidirectional, event-driven channel to classic WebDriver
- Selenium 4.4x exposes BiDi classes (currently beta) for console/log events, network interception and script pinning, closing the capability gap with Playwright/CDP
- Enable it per session with the `webSocketUrl: true` capability

## 5. Session & Context Management

### Selenium – RemoteWebDriver session
```java
public class DriverFactory {
    private static final ThreadLocal<WebDriver> DRIVER = new ThreadLocal<>();

    public static WebDriver create(String browser, URL gridUrl) throws Exception {
        MutableCapabilities caps = switch (browser) {
            case "firefox" -> new FirefoxOptions();
            case "edge" -> new EdgeOptions();
            default -> new ChromeOptions();
        };
        WebDriver driver = gridUrl != null
            ? new RemoteWebDriver(gridUrl, caps)
            : new ChromeDriver((ChromeOptions) caps);
        DRIVER.set(driver);
        return driver;
    }

    public static WebDriver get() { return DRIVER.get(); }

    public static void quit() {
        if (DRIVER.get() != null) {
            DRIVER.get().quit();
            DRIVER.remove();
        }
    }
}
```

### Playwright – isolated contexts per test (built-in)
```typescript
import { test as base } from '@playwright/test'

export const test = base.extend<{ authedPage: import('@playwright/test').Page }>({
  authedPage: async ({ browser }, use) => {
    const context = await browser.newContext({ storageState: 'auth/admin.json' })
    const page = await context.newPage()
    await use(page)
    await context.close()
  },
})
```
- Playwright never reuses cookies/localStorage/cache between tests unless you explicitly load a `storageState` — this is what makes tests parallel-safe by default
- Selenium sessions are heavier: prefer one driver instance per test method/thread, never share a `WebDriver` across parallel threads

## 6. Element Location Strategies

### Comprehensive Locator Guide (Selenium `By`)
- `By.id("submit-btn")` — fastest, use whenever the app provides stable IDs
- `By.cssSelector("[data-testid='checkout-cta']")` — prefer test-id attributes over classes
- `By.xpath("//button[contains(., 'Add to cart')]")` — needed for text-based or axis-based lookups
- `By.linkText("Sign out")` / `By.partialLinkText("Sign")`
- `By.name("email")`, `By.tagName("input")`, `By.className("price-tag")`

### Selenium 4 Relative Locators
```java
import static org.openqa.selenium.support.locators.RelativeLocator.with;

WebElement emailLabel = driver.findElement(By.xpath("//label[text()='Email']"));
WebElement emailInput = driver.findElement(
    with(By.tagName("input")).below(emailLabel)
);
WebElement submit = driver.findElement(
    with(By.tagName("button")).toRightOf(By.cssSelector(".cancel-btn"))
);
```
- Relative locators (`above`, `below`, `toLeftOf`, `toRightOf`, `near`) resolve on the browser's live bounding-box geometry — invaluable for icon buttons and unlabeled inputs with no stable attributes

### Playwright Locators (auto-retrying, preferred over raw selectors)
```typescript
// Role and accessible-name based — resilient to markup changes, mirrors how users perceive the page
await page.getByRole('button', { name: 'Add to cart' }).click()
await page.getByLabel('Email address').fill('qa@example.com')
await page.getByPlaceholder('Search products').fill('wireless mouse')
await page.getByText('Order confirmed', { exact: false }).waitFor()
await page.getByTestId('checkout-summary').isVisible()

// Chaining and filtering
await page.getByRole('listitem')
  .filter({ hasText: 'In stock' })
  .getByRole('button', { name: 'Buy now' })
  .click()
```

### Shadow DOM & Web Components
```typescript
// Playwright pierces open shadow roots automatically with normal locators
await page.locator('custom-datepicker').getByRole('button', { name: 'Next month' }).click()
```
```java
// Selenium 4 exposes the shadow root explicitly
SearchContext shadowRoot = driver.findElement(By.cssSelector("custom-datepicker")).getShadowRoot();
WebElement nextBtn = shadowRoot.findElement(By.cssSelector("button.next"));
```

## 7. Actions & Interactions

### Selenium Actions API (mouse/keyboard/wheel)
```java
Actions actions = new Actions(driver);
actions.moveToElement(menuItem)
    .pause(Duration.ofMillis(200))
    .click(subMenuItem)
    .keyDown(Keys.SHIFT)
    .click(secondItem)
    .keyUp(Keys.SHIFT)
    .perform();

// Drag and drop
actions.dragAndDrop(sourceCard, targetColumn).perform();

// Scroll wheel
actions.scrollByAmount(0, 800).perform();
```

### Playwright interactions (auto-waiting, actionability checks built in)
```typescript
await page.getByRole('textbox', { name: 'Card number' }).fill('4242424242424242')
await page.getByRole('combobox', { name: 'Country' }).selectOption('US')
await page.getByRole('checkbox', { name: 'Save card' }).check()
await page.mouse.wheel(0, 1200)
await page.getByTestId('kanban-card-12').dragTo(page.getByTestId('column-done'))

// Keyboard sequences
await page.keyboard.press('Control+A')
await page.keyboard.type('Replacing selected text', { delay: 30 })
```
- Before any action, Playwright verifies the element is attached, visible, stable (not animating), receives events (not obscured) and enabled — eliminating most flaky `ElementClickInterceptedException`-style failures without extra wait code

## 8. Waits & Synchronization

### Selenium – explicit and fluent waits
```java
WebDriverWait wait = new WebDriverWait(driver, Duration.ofSeconds(15));
wait.until(ExpectedConditions.elementToBeClickable(By.id("checkout-btn"))).click();

Wait<WebDriver> fluentWait = new FluentWait<>(driver)
    .withTimeout(Duration.ofSeconds(20))
    .pollingEvery(Duration.ofMillis(250))
    .ignoring(NoSuchElementException.class)
    .ignoring(StaleElementReferenceException.class);

fluentWait.until(d -> d.findElement(By.cssSelector(".toast-success")).isDisplayed());
```

### Never use `Thread.sleep` / fixed waits
```java
// ❌ Brittle — either too slow (wastes CI minutes) or too fast (flaky)
Thread.sleep(3000);

// ✅ Wait for a real, observable condition
wait.until(ExpectedConditions.invisibilityOfElementLocated(By.cssSelector(".spinner")));
```

### Playwright web-first assertions (auto-retry until timeout)
```typescript
import { expect } from '@playwright/test'

await expect(page.getByTestId('cart-count')).toHaveText('3')
await expect(page.getByRole('alert')).toBeVisible()
await expect(page).toHaveURL(/\/order\/\d+\/confirmation/)
await expect.poll(async () => (await api.get('/orders/latest')).status).toBe(200)
```
- `expect()` assertions retry internally (default 5s, configurable) — no manual polling loops needed for 95% of cases
- Use `expect.soft.poll(...)` (1.61+) to poll a custom condition without failing the test immediately, collecting soft-assertion failures at the end of the test

## 15. Advanced Testing Patterns

### Page Object Model (Playwright, TypeScript)
```typescript
export class CheckoutPage {
  constructor(private page: import('@playwright/test').Page) {}

  private cardNumber = () => this.page.getByLabel('Card number')
  private placeOrderBtn = () => this.page.getByRole('button', { name: 'Place order' })

  async payWithCard(number: string, expiry: string, cvc: string) {
    await this.cardNumber().fill(number)
    await this.page.getByLabel('Expiry').fill(expiry)
    await this.page.getByLabel('CVC').fill(cvc)
    await this.placeOrderBtn().click()
  }

  async expectOrderConfirmed() {
    await expect(this.page.getByRole('heading', { name: /order confirmed/i })).toBeVisible()
  }
}
```

### Component Object Model + Fixtures (composition over inheritance)
```typescript
type Fixtures = { checkoutPage: CheckoutPage; catalogPage: CatalogPage }

export const test = base.extend<Fixtures>({
  checkoutPage: async ({ page }, use) => use(new CheckoutPage(page)),
  catalogPage: async ({ page }, use) => use(new CatalogPage(page)),
})

test('guest can complete checkout', async ({ catalogPage, checkoutPage }) => {
  await catalogPage.addToCart('Wireless Mouse')
  await catalogPage.goToCheckout()
  await checkoutPage.payWithCard('4242424242424242', '12/29', '123')
  await checkoutPage.expectOrderConfirmed()
})
```

### Selenium Page Factory (Java)
```java
public class LoginPage {
    private final WebDriver driver;

    @FindBy(id = "username") private WebElement username;
    @FindBy(id = "password") private WebElement password;
    @FindBy(css = "button[type='submit']") private WebElement submitBtn;

    public LoginPage(WebDriver driver) {
        this.driver = driver;
        PageFactory.initElements(driver, this);
    }

    public DashboardPage loginAs(String user, String pass) {
        username.sendKeys(user);
        password.sendKeys(pass);
        submitBtn.click();
        return new DashboardPage(driver);
    }
}
```

### Common flaky-test root causes
- Element found but not yet interactable (animation/transition in flight) — use actionability waits, not `presenceOfElementLocated`
- Stale element references after a SPA re-render — re-locate rather than caching `WebElement`/`Locator` results across navigations
- Race between test assertion and async API call the UI is waiting on — assert on the UI state, not on a fixed delay
- Shared test data across parallel workers — isolate fixtures per worker/test (unique emails, DB schemas, or API-seeded state)

## 20. Best Practices & Guidelines

### Code Organization & Maintainability
- Prefer role/label-based locators (`getByRole`, `getByLabel`) over brittle CSS/XPath chains — they double as accessibility checks
- One assertion focus per test; compose reusable fixtures/page objects instead of copy-pasting setup steps
- Keep test data self-sufficient: seed via API calls in `beforeEach`, never depend on execution order or shared UI state
- Tag suites (`@smoke`, `@regression`, `@critical-path`) and wire tag-based CI stages so PR feedback stays fast while nightly runs stay thorough
- Fail builds on new flaky tests (`testConfig.failOnFlakyTests` / `--fail-on-flaky-tests`) instead of silently retrying forever
- Version-pin browser/driver images in CI (`selenium/node-chrome:4.46.0`, Playwright's bundled browsers) to avoid "works on my machine" drift
- Store secrets (`QA_USER`, API keys) in the CI secret manager, never in the repo or Selenium capabilities payloads
- Treat `trace: 'retain-on-failure'` and video-on-failure as mandatory in CI — they cut triage time from hours to minutes
