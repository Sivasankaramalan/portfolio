## 1. Environment Setup

### Prerequisites
- Java: JDK 17+ (REST Assured 6.x baseline; use 5.5.x if pinned to Java 8-11)
- Node.js: v18+ LTS (Newman, Supertest, k6 browser module tooling)
- Postman Desktop or Postman CLI for collection authoring
- Docker (for WireMock, Pact Broker, and local database fixtures)

### System Requirements
```bash
# macOS
brew install openjdk@17 node
npm install -g newman newman-reporter-htmlextra
brew install --cask postman

# Linux (CI runners)
sudo apt update && sudo apt install -y openjdk-17-jdk nodejs npm
npm install -g newman
```

### Choosing a Stack
- REST Assured (Java): the standard for teams already on JUnit/TestNG, fluent Given/When/Then DSL, integrates directly with Maven/Gradle build pipelines
- Postman + Newman: fastest path from exploratory testing to a CI-runnable collection, best for cross-team/non-engineer collaboration
- Supertest / Playwright `APIRequestContext` (JS/TS): best when API tests live in the same repo/language as the frontend E2E suite
- pytest + `requests`/`httpx` (Python): common in data platform and ML-adjacent teams

## 2. Architecture & Core Concepts

### REST Fundamentals
- Resources are nouns (`/orders/{id}`), verbs are HTTP methods (`GET`, `POST`, `PUT`, `PATCH`, `DELETE`)
- Statelessness: every request carries all context needed (auth token, correlation ID) — no server-side session reliance
- HATEOAS (rarely fully implemented, but worth checking for): responses may include `_links` to guide client navigation
- Idempotency: `GET`, `PUT`, `DELETE` must be safely retryable; `POST` typically is not unless an `Idempotency-Key` header is honored

### HTTP Status Code Contract
```text
2xx Success        200 OK · 201 Created · 202 Accepted · 204 No Content
3xx Redirection    301 Moved Permanently · 304 Not Modified
4xx Client Error   400 Bad Request · 401 Unauthorized · 403 Forbidden
                   404 Not Found · 409 Conflict · 422 Unprocessable Entity · 429 Too Many Requests
5xx Server Error   500 Internal Server Error · 502 Bad Gateway · 503 Service Unavailable
```

### REST vs GraphQL vs gRPC
- REST: resource-oriented, cacheable via HTTP semantics, many endpoints, over/under-fetching is common
- GraphQL: single endpoint, client specifies exact shape of the response, strongly typed schema (SDL), introspectable
- gRPC: binary Protobuf over HTTP/2, contract-first `.proto` files, best for internal service-to-service calls needing low latency

## 6. Response Validation Strategies

### Status, headers, body assertions (Given/When/Then DSL)
```java
given()
    .pathParam("orderId", orderId)
.when()
    .get("/v2/orders/{orderId}")
.then()
    .statusCode(200)
    .contentType(ContentType.JSON)
    .header("Cache-Control", containsString("no-store"))
    .body("id", equalTo(orderId))
    .body("items", hasSize(greaterThan(0)))
    .body("total", closeTo(49.98, 0.01))
    .time(lessThan(800L));
```

## 9. Waits, Retries & Async Consistency

### Polling for eventual consistency (async processing pipelines)
```java
Awaitility.await()
    .atMost(Duration.ofSeconds(15))
    .pollInterval(Duration.ofMillis(500))
    .untilAsserted(() ->
        given().pathParam("orderId", orderId)
            .when().get("/v2/orders/{orderId}")
            .then().body("status", equalTo("SHIPPED"))
    );
```

### Retry with exponential backoff for flaky/rate-limited dependencies
```typescript
async function withRetry<T>(fn: () => Promise<T>, attempts = 5): Promise<T> {
  for (let i = 0; i < attempts; i++) {
    try { return await fn() }
    catch (err) {
      if (i === attempts - 1) throw err
      await new Promise((r) => setTimeout(r, 2 ** i * 200))
    }
  }
  throw new Error('unreachable')
}
```

### Handling `429 Too Many Requests` correctly in tests
```java
.then()
    .statusCode(anyOf(is(200), is(429)))
    .extract().response();
// If 429, assert Retry-After header is present and respect it before the next call
```

## 11. Contract Testing

### Consumer-driven contract with Pact (JS consumer)
```typescript
import { PactV3, MatchersV3 } from '@pact-foundation/pact'
const { like, integer } = MatchersV3

const provider = new PactV3({ consumer: 'web-app', provider: 'orders-service' })

test('gets an order by id', () =>
  provider
    .given('order 123 exists')
    .uponReceiving('a request for order 123')
    .withRequest({ method: 'GET', path: '/v2/orders/123' })
    .willRespondWith({
      status: 200,
      body: { id: '123', status: like('CONFIRMED'), total: integer(4998) },
    })
    .executeTest(async (mockServer) => {
      const res = await fetch(`${mockServer.url}/v2/orders/123`)
      expect(res.status).toBe(200)
    }))
```

### Provider verification (Java)
```java
@Provider("orders-service")
@PactBroker(url = "https://pact-broker.internal.example.com")
class OrdersProviderContractTest {
    @State("order 123 exists")
    void orderExists() { ordersFixture.seed(new Order("123", "CONFIRMED", 4998)); }

    @TestTemplate
    @ExtendWith(PactVerificationInvocationContextProvider.class)
    void verify(PactVerificationContext context) { context.verifyInteraction(); }
}
```

### Deployment gating with `can-i-deploy`
```bash
pact-broker can-i-deploy \
  --pacticipant orders-service --version $GIT_SHA \
  --to-environment production
```
- Use the git commit SHA as the application version — reused/ambiguous versions corrupt the compatibility matrix
- Only assert fields you actually consume; let matchers (`like`, `regex`, `eachLike`) handle types instead of hardcoding literals
- Roll new consumer expectations out as pending/WIP pacts first so they give feedback without instantly blocking the provider's pipeline

## 14. Security Testing

### OWASP API Security Top 10 – automatable checks
- **Broken Object Level Authorization (BOLA)**: request another tenant's resource ID with your token and assert `403`/`404`, never `200`
- **Broken Authentication**: assert expired/tampered/`alg:none` JWTs are rejected with `401`
- **Excessive Data Exposure**: assert responses never leak internal fields (`passwordHash`, `internalNotes`) regardless of role
- **Rate Limiting**: burst requests past the documented limit and assert `429` + `Retry-After`
- **Mass Assignment**: submit unexpected fields (`role: "ADMIN"`) in a create/update payload and assert they're ignored, not applied

### BOLA regression test

## 15. Advanced Testing Patterns

### Fluent request builder (domain-specific API client)
```java
public class OrdersApiClient {
    private final RequestSpecification spec;
    public OrdersApiClient(RequestSpecification spec) { this.spec = spec; }

    public Response create(OrderPayload payload) {
        return given().spec(spec).body(payload).post("/v2/orders");
    }
    public Response pay(String orderId) {
        return given().spec(spec).post("/v2/orders/{id}/pay", orderId);
    }
    public OrderResponse getConfirmed(String orderId) {
        return given().spec(spec).get("/v2/orders/{id}", orderId)
            .then().statusCode(200).extract().as(OrderResponse.class);
    }
}
```

### Common root causes of flaky API tests
- Shared mutable fixtures across parallel test classes (two tests racing to update the same order ID)
- Asserting on wall-clock timestamps without tolerance for clock skew between test runner and server
- Not accounting for cache headers (`ETag`, `Cache-Control`) causing stale reads immediately after a write
- Test environment data drift — reseed or use ephemeral per-run data instead of assuming fixed seed IDs persist

### Choosing between k6, Gatling and JMeter
- k6: JavaScript/TypeScript scripting, single static Go binary, native CI threshold gating with non-zero exit codes, tightest Grafana/Prometheus integration — default choice for API/microservice load testing in 2026
- Gatling: JVM-native, async engine, best-in-class automatic HTML reports, ideal when the team already ships Java/Scala/Kotlin
- JMeter: broadest legacy protocol coverage (JDBC, JMS, LDAP, SOAP), GUI-first authoring, still the right call when non-developers own performance testing or protocol breadth is non-negotiable

## 20. Best Practices & Guidelines

### Code Organization & Maintainability
- Centralize base URLs, auth, and headers in a shared request specification/API client — never duplicate boilerplate per test class
- Validate contract shape (JSON Schema) separately from business-value assertions (specific field values) so schema drift and logic bugs surface as distinct failures
- Treat GraphQL error arrays as first-class assertions — a `200` with a populated `errors[]` is still a failure your suite must catch
- Keep performance thresholds (`p95`, error rate) in version control next to the load scripts so regressions show up as a diff, not tribal knowledge
- Gate deployments on contract verification (`can-i-deploy`) in addition to functional test suites — passing tests do not guarantee compatibility with what's actually deployed
- Run security-classed checks (BOLA, mass assignment, rate limiting) as a standing regression suite, not a one-off pentest exercise
- Prefer ephemeral, API-seeded test data over long-lived fixtures — deterministic setup/teardown is what makes parallel execution safe
- Log full request/response only on failure (`log().ifValidationFails()`, Newman `--reporter-cli-no-summary` off) to keep CI output signal-heavy, not noisy
